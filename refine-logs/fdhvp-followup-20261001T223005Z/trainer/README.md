# FD/HVP component follow-up trainer

Run `component_horizon.py --source FROZEN_SOURCE --config CONFIG --output-dir FRESH_OUTPUT`; optional `--max-tasks`, `--max-epochs`, `--max-batches` shorten only smoke execution, not the 50-epoch cosine schedule. Model, DataManager, task loop, loss, head expansion and native checkpoint format still come from the unchanged frozen source. Existing checkpoint paths and task-matrix outputs remain the same as the component campaign.

The four new configuration fields are `component_first_response` and `component_second_response` (fd/hvp, default fd), `component_lambda_corr` (positive finite, default1), and `component_attention_backend` (native/math, default native). Any HVP requires UG and math. FD/HVP controls must both use math; native-FD is a separate backend control. The runner supports all four first/second combinations; external queues decide which are conditionally released. No job is launched by this module merely by import.

UG selects g0 + lambda_corr*(g3-g2), or g0 + lambda_corr*rho*H(theta2)*stopgrad(N_eps(g2)). First HVP, if configured, replaces only the response used to construct the outer ascent by rho*H(theta0)*stopgrad(N_eps(g0)); true native g1 remains cached. Both HVP variants retain clean + four native closures, including g3 for comparisons. Native probe operations, including FP32 perturb/unperturb order, are validated against the selected first response. HVP evaluates the captured actual closure point, not a reconstructed ideal theta+r*v. The helper restores the state at entry AFTER the original closure; it does not rewind its RNG consumption.

US coefficient scans select g0 + lambda_corr*(g1-g0) when lambda_corr is not1. At1, the exact native g1 is retained as the floating-point identity control. US coefficients other than1 are not identity controls and, in matched mode, solve a step scalar like any other candidate. U0/UO/UFull require coefficient1.

Natural uses nominal SGD LR. Matched uses the current candidate's own native projected-g1 counterfactual actual FP32 step after native unperturb. The target includes unscaled LoRA BA and all seen FC weight/bias, matching to actual relative error <=1e-3. This is not an independent-S-trajectory target. Selected-gradient, projector and actual same-dtype SGD gates remain exact; three gradient hashes bind the selected value through projector to the actual SGD input. Scalar matching does not change gradient direction or native first probe construction.

HVP direction must be detached and exactly equal to the native-normalized local gradient. HVP first derivatives must agree with that same native closure's CE/gradient before the Hessian result is accepted. Math SDPA dispatch flags are recorded and enforced (math true, flash/memory-efficient/cuDNN false). Unsupported second derivatives raise; there is no silent FD fallback. A missed rho multiplier is rejected independently by the actual correction-to-HVP norm check. No differentiation through normalization or the outer probe-generation graph is performed. The Hessian coordinates are LoRA factors and FC, not effective BA.

Execution accounting: native `training_ce_gradient_passes` remains5 per batch. `training_forward_count` is the total5+nHVP and `native_training_forward_count` is5. `response_audit.hvp_forward_count`, `hvp_first_derivative_passes` and `hvp_second_derivative_passes` are each nHVP (0/1/2). Cumulative counters are `hvp_forward_passes`, `hvp_first_derivative_passes`, `hvp_second_derivative_passes`, `total_training_forward_passes`. HVP thus adds two autograd derivative passes per HVP; it is not equal wall-clock cost to FD.

Each trace adds `response_audit` containing the response protocol, backend flags, native point checks, correction geometry and `hvp_reports.first/second`. Each HVP report includes stage original/outer, closure index0/2, native CE and replay error, same-point gradient comparison, detached direction identity, rho multiplication, norm, and six exact restore flags. `gradient_flow` contains selected expected/actual and projected expected/actual/SGD hashes. Summary and checkpoint manifest contain all four config fields at top level and under `response_config`; summary pins `hvp_helpers_sha256` and `curvature_primitives_sha256`. Successful completion checks cumulative HVP and native forward budgets.

CPU validation: `CUDA_VISIBLE_DEVICES='' python test_fdhvp_cpu.py --output FDHVP_CPU_AUDIT.json` covers32 native-GAM updates across all four response combinations and both scales,12 US/UG coefficient cases, actual projected update/SGD matching, an independent softmax Hessian formula, independent same-point H2 recomputation, exact equality of the first three points/gradients when replacing only the second response,12 negative controls, and two synthetic Controller task0-to1 lifecycles. `test_component_cpu.py` repeats the prior40-step native component regression. These tests do not load the full ViT or exercise GPU double backward; the queue must still pass isolated GPU smokes before formal HVP training.
