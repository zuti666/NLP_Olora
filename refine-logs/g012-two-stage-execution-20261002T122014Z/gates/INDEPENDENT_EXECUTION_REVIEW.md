## Required fixes

### R1. HVP completion validation trusts two summary flags

Evidence: `validate_job.py:9-14` accepts a report solely on `status == passed` and `full_stage2_allowed`. It does not verify backend, seed, source/code/config/reference hashes, tasks 0/4/9, two batches per task, Hstart/Hmid derivative checks, adjacent finite-difference acceptance, state restoration, or zero optimizer updates.

A CPU-only, in-memory mock reproduced acceptance of a report with `backend=native`, `seed=999`, `tasks={}`, `initial_feasibility_only=true`, `optimizer_updates=12`, and the two passing flags for a math full-gate job. This is an artifact-validation defect, not a claim that the current gate script fabricated evidence. The pinned `hvp_gate.py` itself computes its full-gate flag correctly (`hvp_gate.py:214-216`).

Required remedy: independently verify and recompute the task/batch coverage, frozen numerical criteria and all restoration/zero-update assertions from the report; bind the report to the declared job backend, source, reference checkpoints and config. Missing required fields must fail.

### R2. Training completion validation can accept the wrong executed condition

Evidence: `validate_job.py:19-50` checks summary condition fields, aggregate four-gradient count, a few trace fields and matrix shape. It does not check required scientific-check keys, finite trace values, per-row backend/branch/direction/mode/seed, HVP/create-graph/reference counts, task/epoch/batch coverage, or the per-step restoration report. `checks` may contain only a single true value (`validate_job.py:33-35`).

A CPU-only in-memory mock reproduced acceptance of a claimed math Hstart run whose HVP/create-graph counts were zero and whose trace used native/g0, assigned every step to task 0, and included NaN `train_ce`, while `checks` contained only `finite=true`. Again this is a validator blind spot; the reviewed trainer does call the HVP observer correctly (`four_probe_train.py:106-138`).

Required remedy: require the exact mandatory check keys and their true values; reject nonfinite trace content; validate every row against the job, all four ordinary gradient calls and one SGD update, response-specific HVP/create-graph/reference accounting, complete task/epoch/batch coverage and state-restoration checks. Verify input/trainer/trace/matrix/checkpoint receipts against the frozen campaign.

### R3. Crash window prevents reliable queue recovery

Evidence: `run_queue.py:140-161` creates the runtime job directory, writes `job.json`, opens the log and launches a detached worker before persisting `status=running` and its process identity. Restart recovery only attaches jobs already persisted as running (`run_queue.py:63-75`), while a pending job always executes `mkdir(..., exist_ok=False)` (`run_queue.py:140`).

If the controller exits after creating the directory or launching the worker but before saving queue state, the restarted queue sees pending plus an existing directory and fails. A live detached worker is not adopted. The inherited GPU lease protects its GPU from another queue launch, but does not repair the state machine. Reusing nonempty outputs is correctly refused, so deleting the directory and silently rerunning is not an acceptable recovery strategy.

Required remedy: persist a launch-intent state and immutable job record before process creation; have the worker publish its own identity/start receipt immediately; reconcile launching/pending entries from process/start/exit receipts on controller restart. If the worker died with no valid completion evidence, preserve outputs and mark interrupted/failed explicitly rather than relaunching as fresh.

### R4. Recovery can crash on a null process identity

Evidence: `run_queue.py:159` persists the result of `proc_identity(worker.pid)`, which legitimately returns None for an already-exited/zombie process (`common.py:82-91`). After restart, `run_queue.py:74` passes this record to `process_matches`; `common.py:94-96` unconditionally indexes `record["pid"]`. Independent CPU invocation `process_matches(None)` reproduced `TypeError: 'NoneType' object is not subscriptable`. A very fast worker failure or exit can therefore prevent the queue from inspecting its valid exit receipt.

Required remedy: treat a missing/null/malformed process identity as not alive and reconcile the worker/runner start/exit receipts. Do not infer successful completion without validating the receipt and output artifacts.
