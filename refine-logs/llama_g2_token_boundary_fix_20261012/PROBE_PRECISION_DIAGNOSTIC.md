A reusable no-commit helper is available in `scripts_llama/diagnose_g2_probe_precision.py` as `diagnose_probe_precision(model, trainable_params, batch, lr, fixed_radii=(.05, .2))`. It measures one parameter point and one already-collated batch. The model must have FP32 masters for all floating parameters and buffers. A BF16-master model is explicitly rejected; disabling autocast over BF16 masters is not accepted as the full-FP32 control.

Each forward explicitly disables the autocast weight cache. This prevents stale BF16 weight casts when the helper is called inside an already-active autocast context and changes parameters between probes. Backward explicitly disables ambient autocast as well. Both modes use the same BASE values, dropout/random state, shared descent direction `-N(g0_bf16)`, and `h=lr*||g0_bf16||` from the unclipped gradient. The points are `0, h/2, h, 2h`, plus optional fixed radii. Actual forward/backward responses report the zero-radius replay floor, response norm, norm/radius, relative response, linear residual against h after subtracting the zero-radius floor, and BF16/FP32 response cosine. The trainable-weight BF16 casting proxy is reported separately with coordinate-change fraction, represented displacement norm and direction cosine; it is explicitly marked as unable to prove forward visibility.

The helper calls `torch.autograd.grad` and never creates or steps an optimizer. On success or exception it restores the probe parameter values, pre-existing gradient objects and contents, model buffers, module train/eval flags, and Torch/Python/NumPy RNG. CUDA RNG capture/restoration addresses only the selected model device; it never queries or initializes RNG state on every visible GPU. Every model parameter and buffer must be on that device, and mixed-device models are rejected. It is a single-device mechanism diagnostic; it must not be presented as a DDP effective-batch result or new trained accuracy. The zero-radius observations are actual forward/backward measurements rather than assumptions about FP32 parameter equality.

Fourteen targeted CPU tests passed in `tests/test_g2_probe_precision.py`, including a real custom Llama with local LoRA, exact zero-radius replay, gradient/buffer/RNG preservation, a failure during a nonzero probe, BF16-master rejection, the canonical real-training-example loader, nested-autocast response equivalence, selected-device CUDA RNG calls via CPU mocks, mixed-device rejection, adapter option validation, real-profile prefix defaults, and distinct fixed-radius labels. `PROBE_PRECISION_TINY_CPU.json` contains a bounded random tiny-model CPU run with zero commits, exact parameter/gradient/RNG preservation and zero replay floors in both precisions. This is construction evidence only; whether BF16 swallows a probe in the actual trained 1B/3B setup remains unverified. The CLI help path was checked; no full-size model diagnostic or GPU training was launched.

The CLI accepts a local base directory, optional adapter directory, dataset/sample index and device. It loads master weights as FP32. A fresh base uses new current-task factors. With an adapter, `--trainable-scope new` preserves the loaded historical factors and probes fresh current-task factors; `--trainable-scope saved` probes the saved adapter factors instead. These are explicitly recorded as different parameter points. `--new-rank`, `--lora-alpha`, and `--lora-dropout` apply only to a fresh base; with an adapter, nondefault values are rejected rather than silently ignored, and saved adapter settings are preserved. The CLI does not claim to replay the exact parameter point of a historical live stage. It reconstructs the first zero-shot instruction with the canonical labels/options and uses the corrected decoder token pipeline. `add_task_name=true` and `add_dataset_name=true` default to the actual formal profile; `--no-add-task-name` / `--no-add-dataset-name` make an intentional change, recorded in the diagnostic source metadata.

The initial helper had an autocast cache defect found by independent CPU review: nested BF16 autocast could reuse stale casted weights and report zero response for a nonzero probe. This was fixed with `cache_enabled=False` and a regression that pre-populates the ambient cache, then verifies standalone and nested nonzero probe responses are equal.
